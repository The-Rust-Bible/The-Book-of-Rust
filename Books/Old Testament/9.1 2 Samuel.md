## Chapter 1: Cargo Fundamentals

Create a new binary project with `cargo new my_project`. This creates:
   ```text
   my_project/
   â”œâ”€â”€ Cargo.toml
   â””â”€â”€ src/
       â””â”€â”€ main.rs
   ```

Create a new library project with `cargo new --lib my_library`. This creates `src/lib.rs` instead of `src/main.rs`.

The common Cargo commands:
   ```bash
   cargo build           # compile the project
   cargo build --release # compile with optimizations
   cargo run             # compile and run
   cargo check           # check without producing binary (fast)
   cargo test            # run all tests
   cargo doc             # generate documentation
   cargo clean           # remove target/ directory
   ```

`cargo check` is the fastest way to verify code compiles. Use it during development instead of `cargo build` for quick feedback.

`cargo run -- args` passes arguments to the binary. After `--`, everything goes to the program.

`cargo build --release` enables optimizations. Debug builds are faster to compile but slower to run. Release builds are the opposite.

The `target/` directory holds build artifacts. Add it to `.gitignore`:
   ```gitignore
   /target
   ```

`Cargo.lock` locks exact dependency versions. Commit it for binaries, but library crates typically do not commit it (the lock file is for the application, not the library).

`cargo update` updates dependencies to the latest compatible versions. `cargo update -p serde` updates only `serde`.

`cargo metadata` outputs project information as JSON. Useful for tooling and scripts.

## Chapter 2: The Cargo.toml Manifest

The `[package]` section defines your package:
   ```toml
   [package]
   name = "my_project"
   version = "0.1.0"
   edition = "2024"
   authors = ["Your Name <you@example.com>"]
   description = "A short description of your project"
   license = "MIT"
   repository = "https://github.com/you/my_project"
   ```

The `name` field is the crate name. It must be unique on crates.io if you plan to publish.

The `version` field follows semantic versioning: `MAJOR.MINOR.PATCH`:
   - MAJOR: incompatible API changes
   - MINOR: new functionality, backward compatible
   - PATCH: bug fixes, backward compatible

The `edition` field selects the Rust edition: `"2015"`, `"2018"`, `"2021"`, or `"2024"`. Use `"2024"` for new projects.

The `[dependencies]` section lists your project's dependencies:
   ```toml
   [dependencies]
   serde = "1.0"
   tokio = { version = "1", features = ["full"] }
   regex = "1.10"
   ```

Version strings can be exact (`=1.0.0`), tilde (`~1.0.0` â€” allows patch updates), caret (`^1.0.0` â€” the default, allows minor and patch updates), or wildcard (`*`).

The caret `^` is the default. `"1.0"` is shorthand for `^1.0`, meaning `>=1.0.0, <2.0.0`.

Use `cargo add serde` to add a dependency. This updates `Cargo.toml` and downloads the crate automatically:
   ```bash
   cargo add serde
   cargo add tokio --features full
   ```

Features are optional capabilities of a crate. Enable them with the `features` key:
   ```toml
   [dependencies]
   serde = { version = "1.0", features = ["derive"] }
   ```

Use `default-features = false` to disable default features:
   ```toml
   [dependencies]
   tokio = { version = "1", default-features = false, features = ["rt", "net"] }
   ```

`[dev-dependencies]` are used for tests, examples, and benchmarks. They are not included in the final binary:
   ```toml
   [dev-dependencies]
   criterion = "0.5"
   pretty_assertions = "1"
   ```

`[build-dependencies]` are used by `build.rs` build scripts:
   ```toml
   [build-dependencies]
   cc = "1.0"
   ```

`[target.'cfg(...)'.dependencies]` for platform-specific dependencies:
   ```toml
   [target.'cfg(windows)'.dependencies]
   winapi = "0.3"

   [target.'cfg(unix)'.dependencies]
   libc = "0.2"
   ```

## Chapter 3: Profiles and Build Configuration

Profiles customize build settings. The four built-in profiles are `dev`, `release`, `test`, and `bench`:
   ```toml
   [profile.dev]
   opt-level = 0
   debug = true

   [profile.release]
   opt-level = 3
   debug = false
   lto = true
   codegen-units = 1
   panic = "abort"
   ```

`opt-level` controls optimization: 0 (none), 1 (basic), 2 (moderate), 3 (full), `"s"` (size), `"z"` (aggressive size).

`debug` controls debug symbols: `true`, `false`, or a number (0-2).

`lto` enables link-time optimization: `false`, `"thin"`, `"fat"`, or `"off"`. Fat LTO produces the fastest but slowest-compiling binary.

`codegen-units` controls parallelism during codegen. Default is 16 for dev, 1 for release (slower but more optimized).

`panic` can be `"unwind"` (default) or `"abort"`. Abort produces smaller binaries but no backtraces on panic.

Custom profiles inherit from a base profile:
   ```toml
   [profile.release-fast]
   inherits = "release"
   lto = "fat"
   codegen-units = 1
   ```
   Build with: `cargo build --profile release-fast`

`strip = true` removes symbol names from the binary, reducing size. Useful for production releases.

The `incremental` option speeds up rebuilds in dev mode. Default is `true` for dev, `false` for release.

## Chapter 4: Workspaces and Publishing

A workspace is a collection of related packages that share a single `target/` directory and `Cargo.lock`:
   ```toml
   [workspace]
   members = ["crate_a", "crate_b", "crate_c"]
   resolver = "2"
   ```

The workspace root has a `Cargo.toml` with `[workspace]` and each member has its own `[package]`:
   ```text
   my_workspace/
   â”œâ”€â”€ Cargo.toml       â† [workspace] members = [...]
   â”œâ”€â”€ Cargo.lock       â† shared lock file
   â”œâ”€â”€ target/          â† shared build directory
   â”œâ”€â”€ crate_a/
   â”‚   â””â”€â”€ Cargo.toml
   â”œâ”€â”€ crate_b/
   â”‚   â””â”€â”€ Cargo.toml
   â””â”€â”€ crate_c/
       â””â”€â”€ Cargo.toml
   ```

Workspace members can depend on each other using `path` dependencies:
   ```toml
   [dependencies]
   crate_a = { path = "../crate_a" }
   ```

Workspaces share dependency versions across all members. Define shared dependencies in `[workspace.dependencies]`:
   ```toml
   [workspace.dependencies]
   serde = "1.0"
   tokio = "1"
   ```

   Then in member crates: `serde.workspace = true`

Build all workspace members with `cargo build --workspace`. Test all with `cargo test --workspace`.

To publish to crates.io, run `cargo publish`. This requires an account on crates.io and an API token configured with `cargo login`.

Before publishing, run `cargo package` to verify the package builds from a clean state. `cargo publish --dry-run` checks without uploading.

Include a `README.md`, `LICENSE`, and documentation. Set `license`, `description`, and `repository` in `Cargo.toml`.

Use `cargo doc --open` to preview documentation locally before publishing.

Semantic versioning is a covenant with your users. Breaking changes require a major version bump. Use `cargo semver-checks` to verify API compatibility.

The `Cargo.toml` `exclude` field removes files from the published package:
   ```toml
   [package]
   exclude = ["tests/", "examples/", ".github/"]
   ```

`cargo install` installs binaries from crates.io:
   ```bash
   cargo install ripgrep
   ```

`cargo search` searches crates.io:
   ```bash
   cargo search serde
   ```

Pin dependency versions in applications with a committed `Cargo.lock`. For libraries, leave `Cargo.lock` out of version control so users resolve their own compatible versions.
