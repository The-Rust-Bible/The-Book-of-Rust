# Book of 2 Samuel

*Rust topic: Cargo, Dependencies, and Cargo.toml*

## Chapter 1: Cargo Fundamentals

1 Create a new binary project with `cargo new my_project`. This creates:
   ```text
   my_project/
   ├── Cargo.toml
   └── src/
       └── main.rs
   ```

2 Create a new library project with `cargo new --lib my_library`. This creates `src/lib.rs` instead of `src/main.rs`.

3 The common Cargo commands:
   ```bash
   cargo build           # compile the project
   cargo build --release # compile with optimizations
   cargo run             # compile and run
   cargo check           # check without producing binary (fast)
   cargo test            # run all tests
   cargo doc             # generate documentation
   cargo clean           # remove target/ directory
   ```

4 `cargo check` is the fastest way to verify code compiles. Use it during development instead of `cargo build` for quick feedback.

5 `cargo run -- args` passes arguments to the binary. After `--`, everything goes to the program.

6 `cargo build --release` enables optimizations. Debug builds are faster to compile but slower to run. Release builds are the opposite.

7 The `target/` directory holds build artifacts. Add it to `.gitignore`:
   ```gitignore
   /target
   ```

8 `Cargo.lock` locks exact dependency versions. Commit it for binaries, but library crates typically do not commit it (the lock file is for the application, not the library).

9 `cargo update` updates dependencies to the latest compatible versions. `cargo update -p serde` updates only `serde`.

10 `cargo metadata` outputs project information as JSON. Useful for tooling and scripts.

## Chapter 2: The Cargo.toml Manifest

1 The `[package]` section defines your package:
   ```toml
   [package]
   name = "my_project"
   version = "0.1.0"
   edition = "2024"
   authors = ["Your Name <you@example.com>"]
   description = "A short description of your project"
   license = "MIT"
   repository = "https://github.com/you/my_project"
   ```

2 The `name` field is the crate name. It must be unique on crates.io if you plan to publish.

3 The `version` field follows semantic versioning: `MAJOR.MINOR.PATCH`:
   - MAJOR: incompatible API changes
   - MINOR: new functionality, backward compatible
   - PATCH: bug fixes, backward compatible

4 The `edition` field selects the Rust edition: `"2015"`, `"2018"`, `"2021"`, or `"2024"`. Use `"2024"` for new projects.

5 The `[dependencies]` section lists your project's dependencies:
   ```toml
   [dependencies]
   serde = "1.0"
   tokio = { version = "1", features = ["full"] }
   regex = "1.10"
   ```

6 Version strings can be exact (`=1.0.0`), tilde (`~1.0.0` — allows patch updates), caret (`^1.0.0` — the default, allows minor and patch updates), or wildcard (`*`).

7 The caret `^` is the default. `"1.0"` is shorthand for `^1.0`, meaning `>=1.0.0, <2.0.0`.

8 Use `cargo add serde` to add a dependency. This updates `Cargo.toml` and downloads the crate automatically:
   ```bash
   cargo add serde
   cargo add tokio --features full
   ```

9 Features are optional capabilities of a crate. Enable them with the `features` key:
   ```toml
   [dependencies]
   serde = { version = "1.0", features = ["derive"] }
   ```

10 Use `default-features = false` to disable default features:
   ```toml
   [dependencies]
   tokio = { version = "1", default-features = false, features = ["rt", "net"] }
   ```

11 `[dev-dependencies]` are used for tests, examples, and benchmarks. They are not included in the final binary:
   ```toml
   [dev-dependencies]
   criterion = "0.5"
   pretty_assertions = "1"
   ```

12 `[build-dependencies]` are used by `build.rs` build scripts:
   ```toml
   [build-dependencies]
   cc = "1.0"
   ```

13 `[target.'cfg(...)'.dependencies]` for platform-specific dependencies:
   ```toml
   [target.'cfg(windows)'.dependencies]
   winapi = "0.3"

   [target.'cfg(unix)'.dependencies]
   libc = "0.2"
   ```

## Chapter 3: Profiles and Build Configuration

1 Profiles customize build settings. The four built-in profiles are `dev`, `release`, `test`, and `bench`:
   ```toml
   [profile.dev]
   opt-level = 0
   debug = true

   [profile.release]
   opt-level = 3
   debug = false
   lto = true
   codegen-units = 1
   panic = "abort"
   ```

2 `opt-level` controls optimization: 0 (none), 1 (basic), 2 (moderate), 3 (full), `"s"` (size), `"z"` (aggressive size).

3 `debug` controls debug symbols: `true`, `false`, or a number (0-2).

4 `lto` enables link-time optimization: `false`, `"thin"`, `"fat"`, or `"off"`. Fat LTO produces the fastest but slowest-compiling binary.

5 `codegen-units` controls parallelism during codegen. Default is 16 for dev, 1 for release (slower but more optimized).

6 `panic` can be `"unwind"` (default) or `"abort"`. Abort produces smaller binaries but no backtraces on panic.

7 Custom profiles inherit from a base profile:
   ```toml
   [profile.release-fast]
   inherits = "release"
   lto = "fat"
   codegen-units = 1
   ```
   Build with: `cargo build --profile release-fast`

8 `strip = true` removes symbol names from the binary, reducing size. Useful for production releases.

9 The `incremental` option speeds up rebuilds in dev mode. Default is `true` for dev, `false` for release.

## Chapter 4: Workspaces and Publishing

1 A workspace is a collection of related packages that share a single `target/` directory and `Cargo.lock`:
   ```toml
   [workspace]
   members = ["crate_a", "crate_b", "crate_c"]
   resolver = "2"
   ```

2 The workspace root has a `Cargo.toml` with `[workspace]` and each member has its own `[package]`:
   ```text
   my_workspace/
   ├── Cargo.toml       ← [workspace] members = [...]
   ├── Cargo.lock       ← shared lock file
   ├── target/          ← shared build directory
   ├── crate_a/
   │   └── Cargo.toml
   ├── crate_b/
   │   └── Cargo.toml
   └── crate_c/
       └── Cargo.toml
   ```

3 Workspace members can depend on each other using `path` dependencies:
   ```toml
   [dependencies]
   crate_a = { path = "../crate_a" }
   ```

4 Workspaces share dependency versions across all members. Define shared dependencies in `[workspace.dependencies]`:
   ```toml
   [workspace.dependencies]
   serde = "1.0"
   tokio = "1"
   ```

   Then in member crates: `serde.workspace = true`

5 Build all workspace members with `cargo build --workspace`. Test all with `cargo test --workspace`.

6 To publish to crates.io, run `cargo publish`. This requires an account on crates.io and an API token configured with `cargo login`.

7 Before publishing, run `cargo package` to verify the package builds from a clean state. `cargo publish --dry-run` checks without uploading.

8 Include a `README.md`, `LICENSE`, and documentation. Set `license`, `description`, and `repository` in `Cargo.toml`.

9 Use `cargo doc --open` to preview documentation locally before publishing.

10 Semantic versioning is a covenant with your users. Breaking changes require a major version bump. Use `cargo semver-checks` to verify API compatibility.

11 The `Cargo.toml` `exclude` field removes files from the published package:
   ```toml
   [package]
   exclude = ["tests/", "examples/", ".github/"]
   ```

12 `cargo install` installs binaries from crates.io:
   ```bash
   cargo install ripgrep
   ```

13 `cargo search` searches crates.io:
   ```bash
   cargo search serde
   ```

14 Pin dependency versions in applications with a committed `Cargo.lock`. For libraries, leave `Cargo.lock` out of version control so users resolve their own compatible versions.
