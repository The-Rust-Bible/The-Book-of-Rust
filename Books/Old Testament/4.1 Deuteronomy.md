## Chapter 1: Panic and Unrecoverable Errors

`panic!` immediately stops the program and unwinds the stack, running destructors along the way:
   ```rust
   fn main() {
       panic!("Something went catastrophically wrong");
   }
   ```

`panic!` is for unrecoverable errors â€” bugs, invariants violated, or situations where continuing is unsafe.

You can include formatting in a panic message:
   ```rust
   panic!("Invalid value: expected positive, got {}", -5);
   ```

`unwrap()` panics if the value is `None` or `Err`. It is fine for prototyping and tests, but risky in production:
   ```rust
   let x: Option<i32> = None;
   // x.unwrap(); // panics!
   ```

`expect()` is like `unwrap()` but provides a custom error message:
   ```rust
   let x: Option<i32> = None;
   // x.expect("x should always be Some in this context"); // panics with that message
   ```

Rust has two panic strategies: `unwind` (the default) and `abort`. Unwind runs destructors; abort stops immediately. Configure in `Cargo.toml`:
   ```toml
   [profile.release]
   panic = "abort"
   ```

Use `std::panic::catch_unwind` to catch panics and prevent them from crashing the program. This is rare in practice â€” most programs should fix bugs, not catch them.

Avoid `unwrap()` and `expect()` on values that come from outside your control â€” user input, file contents, network responses.

It is acceptable to `unwrap()` when:
   - You are writing a test
   - You are in a prototype or example
   - You have proven the value is always `Some`/`Ok` by construction

In production code, prefer `?` or explicit `match` over `unwrap()`.

`assert!` and `assert_eq!` panic if their condition is false. They are primarily used in tests but can also guard invariants in production code.

`debug_assert!` only runs in debug builds. Use it for invariants that are too expensive to check in release mode.

## Chapter 2: The Result Type

`Result<T, E>` represents either success (`Ok(T)`) or failure (`Err(E)`):
   ```rust
   enum Result<T, E> {
       Ok(T),
       Err(E),
   }
   ```

Use `Ok` for success and `Err` for failure:
   ```rust
   fn divide(a: i32, b: i32) -> Result<i32, String> {
       if b == 0 {
           Err(String::from("division by zero"))
       } else {
           Ok(a / b)
       }
   }
   ```

Handle a `Result` with `match`:
   ```rust
   let result = divide(10, 2);
   match result {
       Ok(value) => println!("Result: {value}"),
       Err(e) => println!("Error: {e}"),
   }
   ```

Handle `Ok` with `if let`:
   ```rust
   if let Ok(value) = divide(10, 2) {
       println!("Result: {value}");
   }
   ```

Handle `Err` with `if let`:
   ```rust
   if let Err(e) = divide(10, 0) {
       println!("Error: {e}");
   }
   ```

Use `.unwrap()` to extract the `Ok` value (panics on `Err`). Use `.expect("message")` for a custom panic message.

`.unwrap_or(default)` returns the `Ok` value or a default on `Err`:
   ```rust
   let result = divide(10, 0).unwrap_or(-1); // -1
   ```

`.unwrap_or_else(closure)` computes the default lazily:
   ```rust
   let result = divide(10, 0).unwrap_or_else(|_| compute_fallback());
   ```

`.unwrap_or_default()` returns the default value for `T` if `T` implements `Default`:
   ```rust
   let result: i32 = divide(10, 0).unwrap_or_default(); // 0
   ```

`.map()` transforms the `Ok` value while leaving `Err` untouched:
   ```rust
   let result = divide(10, 2).map(|v| v * 2); // Ok(10)
   ```

`.map_err()` transforms the `Err` value while leaving `Ok` untouched:
   ```rust
   let result = divide(10, 0).map_err(|e| format!("Error: {e}"));
   // Err("Error: division by zero")
   ```

`.and()` returns the second `Result` if the first is `Ok`, or the first `Err`:
   ```rust
   let a: Result<i32, String> = Ok(1);
   let b: Result<i32, String> = Ok(2);
   assert_eq!(a.and(b), Ok(2));
   ```

`.or()` returns the first `Result` if it is `Ok`, otherwise the second:
   ```rust
   let a: Result<i32, String> = Err("error".to_string());
   let b: Result<i32, String> = Ok(42);
   assert_eq!(a.or(b), Ok(42));
   ```

`.ok()` converts `Result<T, E>` to `Option<T>`, discarding the error:
   ```rust
   let opt: Option<i32> = divide(10, 2).ok(); // Some(5)
   ```

`.err()` converts `Result<T, E>` to `Option<E>`, discarding the success value:
   ```rust
   let opt: Option<String> = divide(10, 0).err(); // Some("division by zero")
   ```

`Result` implements `From` for common conversions. Use `.into()` to convert between error types.

## Chapter 3: The Question Mark Operator

The `?` operator is the idiomatic way to propagate errors. It unwraps `Ok` values and returns `Err` early:
   ```rust
   fn read_config(path: &str) -> Result<String, std::io::Error> {
       let content = std::fs::read_to_string(path)?;
       Ok(content)
   }
   ```

If `read_to_string` returns `Err`, the `?` operator immediately returns that error from `read_config`. If it returns `Ok`, the value is unwrapped and execution continues.

`?` only works in functions that return `Result`, `Option`, or a type implementing the `FromResidual` trait.

`?` uses the `From` trait to convert errors automatically. The error type in the function must implement `From` for the error type being propagated:
   ```rust
   fn parse_and_divide(s: &str) -> Result<i32, ParseError> {
       let num: i32 = s.parse()?; // ParseIntError -> ParseError via From
       let result = divide(num, 2)?; // ArithmeticError -> ParseError via From
       Ok(result)
   }
   ```

Chaining `?` makes error handling concise:
   ```rust
   fn read_and_parse(path: &str) -> Result<i32, std::io::Error> {
       let content = std::fs::read_to_string(path)?;
       let num: i32 = content.trim().parse()?;
       Ok(num)
   }
   ```

`?` works with `Option` too, in functions returning `Option`:
   ```rust
   fn get_middle(s: &str) -> Option<char> {
       let chars: Vec<char> = s.chars().collect();
       let mid = chars.len() / 2;
       Some(chars.get(mid)?)
   }
   ```

`?` on an `Option` returns `None` early if the value is `None`.

You cannot use `?` in functions that return `()`, `bool`, or other types that do not implement the required traits. Use `match` or `if let` instead.

`?` desugars to a `match` expression. This is what `read_to_string(path)?` actually does:
   ```rust
   let content = match std::fs::read_to_string(path) {
       Ok(val) => val,
       Err(e) => return Err(From::from(e)),
   };
   ```

In `main`, you can return `Result<(), E>` where `E: std::error::Error` to use `?`:
   ```rust
   fn main() -> Result<(), Box<dyn std::error::Error>> {
       let content = std::fs::read_to_string("hello.txt")?;
       println!("{content}");
       Ok(())
   }
   ```

`Box<dyn std::error::Error>` is the "any error" type. It is convenient for binaries but too vague for libraries â€” prefer specific error types.

## Chapter 4: Custom Error Types

Define custom errors as enums. Each variant represents a specific failure mode:
   ```rust
   #[derive(Debug)]
   enum MathError {
       DivisionByZero,
       Overflow,
       NegativeInput,
   }
   ```

Implement `std::fmt::Display` for human-readable messages:
   ```rust
   impl std::fmt::Display for MathError {
       fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
           match self {
               MathError::DivisionByZero => write!(f, "cannot divide by zero"),
               MathError::Overflow => write!(f, "arithmetic overflow"),
               MathError::NegativeInput => write!(f, "negative input not allowed"),
           }
       }
   }
   ```

Implement `std::error::Error` to make the type a proper error. The `Debug` trait is required:
   ```rust
   impl std::error::Error for MathError {}
   ```

Now `?` works with `MathError` in functions returning `Result<T, MathError>`:
   ```rust
   fn safe_divide(a: i32, b: i32) -> Result<i32, MathError> {
       if b == 0 {
           return Err(MathError::DivisionByZero);
       }
       a.checked_div(b).ok_or(MathError::Overflow)
   }
   ```

Use the `thiserror` crate to reduce boilerplate. Add it to `Cargo.toml`:
   ```toml
   [dependencies]
   thiserror = "2"
   ```

With `thiserror`, derive `Error` instead of implementing it manually:
   ```rust
   use thiserror::Error;

   #[derive(Debug, Error)]
   enum MathError {
       #[error("cannot divide by zero")]
       DivisionByZero,
       #[error("arithmetic overflow")]
       Overflow,
       #[error("negative input: {0}")]
       NegativeInput(i32),
   }
   ```

`thiserror` supports transparent wrapping of underlying errors with `#[error(transparent)]` and `#[from]`:
   ```rust
   #[derive(Debug, Error)]
   enum ConfigError {
       #[error("failed to read config file")]
       Io(#[from] std::io::Error),
       #[error("invalid TOML: {0}")]
       Parse(#[from] toml::de::Error),
   }
   ```

The `#[from]` attribute automatically implements `From<UnderlyingError> for ConfigError`, so `?` works seamlessly.

Use library errors with `Box<dyn Error>` at application boundaries. Use specific error types within libraries.

The `anyhow` crate is useful for applications (not libraries). It provides a flexible error type with context:
   ```rust
   use anyhow::{Context, Result};

   fn read_config(path: &str) -> Result<String> {
       let content = std::fs::read_to_string(path)
           .with_context(|| format!("failed to read {path}"))?;
       Ok(content)
   }
   ```

`Context` adds human-readable context to errors, making debugging easier. The `?` operator propagates the error with its context chain intact.

For libraries, always use specific error types. `anyhow` and `Box<dyn Error>` erase type information that library users need.

The `Option` combinators have parallels for `Result`: `map`, `and_then`, `or`, `or_else`, `unwrap_or`, `unwrap_or_else`.

`and_then` chains fallible operations:
   ```rust
   fn parse(s: &str) -> Result<i32, ParseError> {
       s.trim().parse::<i32>()
           .map_err(|_| ParseError::InvalidNumber)
   }

   fn process(s: &str) -> Result<i32, MathError> {
       parse(s)
           .and_then(|n| safe_divide(100, n))
   }
   ```

When a function has many `?` calls, the error types must all convert into the function's return error type via `From`. Plan your error hierarchy accordingly.

Do not use `unwrap()` in library code. Every `unwrap()` is a potential panic in someone else's program.

Propagate errors with `?`. Handle errors with `match`. Transform errors with `map_err`. Add context with `anyhow::Context` or `thiserror`.

The golden rule: `unwrap()` in tests and examples, `?` in production.
