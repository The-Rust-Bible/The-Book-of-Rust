# Book of 1 Samuel

*Rust topic: Testing — Unit Tests, Integration Tests, and Doc Tests*

## Chapter 1: Unit Tests

1 Unit tests live in the same file as the code they test, inside a `#[cfg(test)]` module:
   ```rust
   pub fn add(a: i32, b: i32) -> i32 {
       a + b
   }

   #[cfg(test)]
   mod tests {
       use super::*;

       #[test]
       fn it_adds_two_numbers() {
           assert_eq!(add(2, 3), 5);
       }
   }
   ```

2 The `#[cfg(test)]` attribute means the module is only compiled when running tests. It has zero impact on the release binary.

3 `use super::*` imports everything from the parent module into the test module.

4 The `#[test]` attribute marks a function as a test. Test functions take no arguments and return `()`.

5 Run tests with `cargo test`. Cargo compiles the code with `--test` and runs all test functions.

6 `assert!` panics if the condition is false:
   ```rust
   assert!(add(2, 3) == 5);
   ```

7 `assert_eq!` panics if the two values are not equal. It prints both values on failure:
   ```rust
   assert_eq!(add(2, 3), 5);
   ```

8 `assert_ne!` panics if the two values are equal:
   ```rust
   assert_ne!(add(2, 3), 6);
   ```

9 Test functions can have descriptive names using snake_case. The test output shows these names.

10 A failing test panics, which unwinds the stack. The test harness catches the panic and reports the failure without crashing the entire test suite.

11 The `-- --nocapture` flag shows `println!` output from tests that pass. By default, stdout from passing tests is captured and hidden.

12 The `-- --test-threads=1` flag runs tests sequentially. By default, Cargo runs tests in parallel threads.

13 Use `#[should_panic]` to test that a function panics:
   ```rust
   #[test]
   #[should_panic]
   fn panics_on_negative() {
       assert!(add(-1, -1) < 0, "should panic");
   }
   ```

14 Use `#[should_panic(expected = "substring")]` to check the panic message:
   ```rust
   #[test]
   #[should_panic(expected = "assertion failed")]
   fn panics_with_expected_message() {
       assert!(false);
   }
   ```

## Chapter 2: Integration Tests

1 Integration tests live in the `tests/` directory at the package root. Each `.rs` file is compiled as a separate crate:
   ```text
   my_package/
   ├── Cargo.toml
   ├── src/
   │   └── lib.rs
   └── tests/
       └── integration_test.rs
   ```

2 Integration tests use the public API of your library. They cannot access private items:
   ```rust
   // tests/integration_test.rs
   use my_package::add;

   #[test]
   fn it_adds_two_numbers() {
       assert_eq!(add(2, 3), 5);
   }
   ```

3 Each file in `tests/` is a separate crate. To share code between integration test files, create a `tests/common/mod.rs`:
   ```rust
   // tests/common/mod.rs
   pub fn setup() -> TestContext {
       TestContext { /* ... */ }
   }
   ```
   Then in each test file: `mod common;`

4 Integration tests test your library as an external user would use it. They test the public API.

5 Unit tests test individual functions and modules in isolation. Integration tests test how the parts work together.

6 Both unit and integration tests run with `cargo test`. Unit tests run first, then integration tests.

7 Use environment variables to configure integration tests:
   ```rust
   #[test]
   fn it_reads_env() {
       let timeout = std::env::var("TEST_TIMEOUT").unwrap_or_else(|_| "30".to_string());
       assert!(!timeout.is_empty());
   }
   ```

8 Skip integration tests in environments where they are not needed using `#[ignore]`:
   ```rust
   #[test]
   #[ignore = "requires a database connection"]
   fn it_connects_to_db() {
       // ...
   }
   ```
   Run ignored tests with `cargo test -- --ignored`.

## Chapter 3: Doc Tests

1 Doc comments with code blocks are automatically tested. This ensures examples in your documentation always compile and produce the documented output:
   ```rust
   /// Adds two numbers.
   ///
   /// # Examples
   ///
   /// ```
   /// let result = my_crate::add(2, 3);
   /// assert_eq!(result, 5);
   /// ```
   pub fn add(a: i32, b: i32) -> i32 {
       a + b
   }
   ```

2 The code block between triple backticks with `rust` (or no language) is compiled and run as a test. If it has no `assert` statements, it must compile but doesn't need to produce output.

3 Use `no_run` to compile but not execute:
   ```rust
   /// ```no_run
   /// let expensive = my_crate::compute();
   /// ```
   ```

4 Use `ignore` to skip a doc test entirely:
   ```rust
   /// ```ignore
   /// let not_yet_implemented = my_crate::future_feature();
   /// ```
   ```

5 Use `should_panic` for doc tests that are expected to panic:
   ```rust
   /// ```should_panic
   /// my_crate::panic_on_purpose();
   /// ```
   ```

6 Hidden lines with `#` are compiled but not displayed:
   ```rust
   /// ```
   /// # use my_crate::Config;
   /// let config = Config::default();
   /// assert!(config.is_valid());
   /// ```
   ```

7 The `text` annotation skips compilation entirely — useful for showing non-Rust code or pseudo-code:
   ```rust
   /// ```text
   /// this is not compiled or run
   /// ```
   ```

8 Doc tests are a powerful way to keep documentation accurate. Every example in your docs is verified by the compiler.

## Chapter 4: Test Organization and Best Practices

1 Test naming convention: `function_name_describes_scenario`. Good names read as documentation:
   ```rust
   #[test]
   fn add_returns_sum_of_two_positive_numbers() { /* ... */ }

   #[test]
   fn add_returns_zero_when_both_are_zero() { /* ... */ }

   #[test]
   fn parse_returns_error_for_empty_string() { /* ... */ }
   ```

2 Arrange-Act-Assert pattern: set up test data, perform the action, assert the result. Separate these with blank lines or comments for readability:
   ```rust
   #[test]
   fn filter_keeps_only_even_numbers() {
       // Arrange
       let numbers = vec![1, 2, 3, 4, 5, 6];

       // Act
       let evens: Vec<i32> = numbers.into_iter().filter(|&x| x % 2 == 0).collect();

       // Assert
       assert_eq!(evens, vec![2, 4, 6]);
   }
   ```

3 Test one thing per test function. If a test fails, its name should tell you exactly what broke.

4 Use helper functions for common setup to reduce duplication:
   ```rust
   fn make_config() -> Config {
       Config {
           timeout: 30,
           retries: 3,
       }
   }

   #[test]
   fn config_with_default_timeout() {
       let config = make_config();
       assert_eq!(config.timeout, 30);
   }
   ```

5 Parameterized tests: use a loop or macro to test multiple cases with one function:
   ```rust
   #[test]
   fn parse_handles_valid_inputs() {
       let cases = vec![
           ("42", 42),
           ("0", 0),
           ("-100", -100),
       ];
       for (input, expected) in cases {
           assert_eq!(input.parse::<i32>().unwrap(), expected);
       }
   }
   ```

6 Test error cases, not just happy paths. Every `Result`-returning function should have tests for both `Ok` and `Err` cases:
   ```rust
   #[test]
   fn parse_rejects_invalid_input() {
       assert!("hello".parse::<i32>().is_err());
       assert!("".parse::<i32>().is_err());
       assert!("3.14".parse::<i32>().is_err());
   }
   ```

7 Test boundary conditions: empty inputs, maximum values, zero, negative numbers, Unicode edge cases.

8 Use `Result<(), Box<dyn Error>>` as the return type for tests that may fail in multiple ways:
   ```rust
   #[test]
   fn reads_file_successfully() -> Result<(), Box<dyn std::error::Error>> {
       let content = std::fs::read_to_string("Cargo.toml")?;
       assert!(content.contains("[package]"));
       Ok(())
   }
   ```

9 Test private functions by placing unit tests in the same module. Test public functions with integration tests in `tests/`.

10 Do not test implementation details. Test the public contract — what the function does, not how it does it. Tests that assert on internal state break when you refactor.

11 The `pretty_assertions` crate provides prettier diff output for failed assertions. Add it as a dev-dependency:
   ```toml
   [dev-dependencies]
   pretty_assertions = "1"
   ```
   Then `use pretty_assertions::assert_eq;` in your test module.

12 The `proptest` or `quickcheck` crates generate random inputs to test properties. Use them for functions where exhaustive manual testing is impractical:
   ```rust
   // With proptest:
   proptest! {
       #[test]
       fn add_is_commutative(a: i32, b: i32) {
           prop_assert_eq!(add(a, b), add(b, a));
       }
   }
   ```

13 `cargo test` runs unit tests, integration tests, and doc tests. Use `cargo test --lib` to run only unit tests, `cargo test --test name` for a specific integration test, and `cargo test --doc` for doc tests only.

14 Continuous integration: run `cargo test` on every commit. Use `cargo tarpaulin` or `llvm-cov` for code coverage. A project with no tests is a project with no safety net.
