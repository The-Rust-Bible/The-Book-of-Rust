# Book of Exodus

*Rust topic: Ownership, Borrowing, References, and Lifetimes*

## Chapter 1: The Law of Ownership

1 In Rust, every value has a variable that is its owner. There can be only one owner at a time.

2 When the owner goes out of scope, the value is dropped and its memory freed automatically:
   ```rust
   {
       let s = String::from("hello");
       // s is valid here
   } // s goes out of scope, memory is freed
   ```

3 Values are either moved or borrowed. A move transfers ownership from one variable to another:
   ```rust
   let s1 = String::from("hello");
   let s2 = s1; // s1 is moved to s2
   // println!("{}", s1); // error: s1 no longer owns the value
   ```

4 For types that implement the `Copy` trait (integers, floats, booleans, chars, and small fixed arrays), assignment copies the value instead of moving:
   ```rust
   let x = 5;
   let y = x; // x is copied, not moved
   println!("{}", x); // valid — x is still usable
   ```

5 Types that are not `Copy` (like `String` and `Vec<T>`) are moved on assignment. Using the original variable afterward is a compile error.

6 The `Clone` trait provides an explicit way to deep-copy a value:
   ```rust
   let s1 = String::from("hello");
   let s2 = s1.clone();
   println!("{}", s1); // valid — s1 was cloned, not moved
   ```

7 `Clone` is not automatic. If a type implements `Clone`, you opt in by calling `.clone()`. Avoid unnecessary clones — they cost memory and time.

8 Ownership rules summary:
   - Each value in Rust has an owner.
   - There can only be one owner at a time.
   - When the owner goes out of scope, the value is dropped.

9 These rules are enforced at compile time by the borrow checker, a core part of `rustc`.

## Chapter 2: Moving Between Scopes

1 Passing a value to a function moves or copies it, just like assignment:
   ```rust
   fn take_ownership(s: String) {
       println!("{}", s);
   } // s is dropped here

   fn make_copy(x: i32) {
       println!("{}", x);
   } // x is dropped here, but the original is unaffected
   ```

2 After `take_ownership(s1)`, `s1` is no longer valid. After `make_copy(x)`, `x` is still usable.

3 Returning values from functions transfers ownership to the caller:
   ```rust
   fn gives_ownership() -> String {
       String::from("hello")
   }

   let s = gives_ownership(); // s takes ownership
   ```

4 When a function returns a value that was passed in, ownership flows back to the caller:
   ```rust
   fn takes_and_gives_back(s: String) -> String {
       s // ownership returned
   }
   ```

5 The pattern of taking ownership, using a value, and returning it is tedious. This is where borrowing comes in.

6 The stack holds values in last-in, first-out order. When a scope ends, values are popped off the stack automatically.

7 The heap holds values whose size may be unknown at compile time or may change. `String`, `Vec`, and `Box` allocate on the heap.

8 When a heap-allocated value goes out of scope, Rust calls `drop` to free the memory. You can run code at this point by implementing the `Drop` trait:
   ```rust
   struct Resource {
       name: String,
   }

   impl Drop for Resource {
       fn drop(&mut self) {
           println!("Dropping {}", self.name);
       }
   }
   ```

9 Rust does not have a garbage collector. Memory is freed deterministically when the owner goes out of scope.

10 Double-free errors, dangling pointers, and memory leaks are prevented at compile time, not runtime.

## Chapter 3: References and Borrowing

1 Instead of transferring ownership, you can lend a value temporarily by taking a reference. This is called borrowing.

2 A reference is written with `&`. An immutable reference allows reading but not mutation:
   ```rust
   let s = String::from("hello");
   let len = calculate_length(&s); // &s is a reference
   println!("{}", s); // s is still valid
   ```

3 The function signature uses `&String` to indicate it borrows rather than takes ownership:
   ```rust
   fn calculate_length(s: &String) -> usize {
       s.len()
   } // s goes out of scope, but the String it points to is not dropped
   ```

4 References are always immutable by default. The value they point to cannot be modified through an immutable reference.

5 To modify a borrowed value, take a mutable reference with `&mut`:
   ```rust
   let mut s = String::from("hello");
   change(&mut s);
   ```

6 The function signature for a mutable borrow uses `&mut`:
   ```rust
   fn change(s: &mut String) {
       s.push_str(", world");
   }
   ```

7 The borrowing rules are strict:
   - At any given time, you can have either one mutable reference or any number of immutable references.
   - References must always be valid (no dangling references).

8 This means you cannot have a mutable reference while an immutable reference exists:
   ```rust
   let mut s = String::from("hello");
   let r1 = &s;   // immutable borrow
   let r2 = &s;   // another immutable borrow — OK
   let r3 = &mut s; // error: cannot borrow s as mutable because it is also borrowed as immutable
   ```

9 You also cannot have two mutable references to the same value:
   ```rust
   let mut s = String::from("hello");
   let r1 = &mut s;
   let r2 = &mut s; // error: cannot borrow s as mutable more than once
   ```

10 The scope of a reference starts where it is introduced and ends the last time it is used. This is called non-lexical lifetimes (NLL):
   ```rust
   let mut s = String::from("hello");
   let r1 = &s;
   println!("{}", r1); // r1's last use is here
   let r2 = &mut s;    // OK — r1 is no longer used
   println!("{}", r2);
   ```

11 Dangling references are impossible in safe Rust. Rust guarantees that references always point to valid data.

## Chapter 4: Slices

1 A slice is a reference to a contiguous sequence of elements in a collection. It is a non-owning view.

2 String slices are written as `&s[start..end]`, where `start` is inclusive and `end` is exclusive:
   ```rust
   let s = String::from("Hello, Rust!");
   let hello = &s[0..5];   // "Hello"
   let rust = &s[7..11];   // "Rust"
   ```

3 You can omit the start or end index to slice from the beginning or to the end:
   ```rust
   let s = String::from("Hello, Rust!");
   let hello = &s[..5];   // from start to index 5
   let rust = &s[7..];    // from index 7 to end
   let whole = &s[..];    // entire string
   ```

4 String slices are always valid UTF-8 boundaries. Slicing at a non-character-boundary index panics at runtime.

5 String literals are string slices pointing into the binary:
   ```rust
   let s = "Hello, world!"; // type: &str
   ```

6 `&str` is the type of a string slice. `String` is an owned, growable string. Most functions accept `&str` to work with both:
   ```rust
   fn first_word(s: &str) -> &str {
       let bytes = s.as_bytes();
       for (i, &item) in bytes.iter().enumerate() {
           if item == b' ' {
               return &s[0..i];
           }
       }
       &s[..]
   }
   ```

7 Array slices work similarly, referencing a portion of an array or vector:
   ```rust
   let arr = [1, 2, 3, 4, 5];
   let slice: &[i32] = &arr[1..3]; // [2, 3]
   ```

8 Slices hold a reference to the data plus its length. They are always passed as references.

## Chapter 5: Lifetimes

1 A lifetime is Rust's way of ensuring references are valid for as long as they are used. Most lifetimes are inferred and hidden.

2 The lifetime annotation `'a` tells the compiler that all references with that annotation must live at least as long as `'a`:
   ```rust
   fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
       if x.len() > y.len() { x } else { y }
   }
   ```

3 The `<'a>` after the function name declares a generic lifetime parameter. The compiler uses it to ensure the returned reference is valid for as long as both inputs are valid.

4 Lifetime elision rules allow the compiler to infer lifetimes in common patterns without explicit annotations:
   - Each parameter that is a reference gets its own lifetime parameter.
   - If there is exactly one input lifetime, that lifetime is assigned to all output lifetimes.
   - If there are multiple input lifetimes but one is `&self` or `&mut self`, the lifetime of `self` is assigned to all outputs.

5 Example of elision — the compiler infers the lifetimes:
   ```rust
   fn first_word(s: &str) -> &str {
       // elided: fn first_word<'a>(s: &'a str) -> &'a str
       let bytes = s.as_bytes();
       for (i, &item) in bytes.iter().enumerate() {
           if item == b' ' {
               return &s[0..i];
           }
       }
       &s[..]
   }
   ```

6 Structs that hold references need lifetime annotations:
   ```rust
   struct Excerpt<'a> {
       part: &'a str,
   }
   ```

7 The `'static` lifetime is the longest possible. It means the reference lives for the entire duration of the program:
   ```rust
   let s: &'static str = "I live forever";
   ```

8 All string literals have `'static` lifetime because they are embedded in the binary.

9 Lifetimes do not change how long a value lives. They describe the relationships between references — which references are valid for how long.

10 When in doubt, let the compiler guide you. Start without lifetime annotations, read the error messages, and add annotations where the compiler tells you to.
